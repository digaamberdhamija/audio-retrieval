Audio retrieval · Audio search

Ask a question, land on the moment that answers it

A search service for recorded conversations between two people. It transcribes each recording with speaker labels and the time of every word, indexes it as overlapping slices of time at three lengths, and searches them by exact words and by meaning. Every answer is a stretch of the original audio: which recording, where to start and stop, who spoke and what they said.

How it works

Index each recording once, then search three window lengths for every question

Strategies

The retrieval decisions behind the results

Each decision answers a specific way that search over spoken conversation goes wrong.

word timestamps

Slice by time, not by speaker turn

Conversations range from rapid back-and-forth to twenty-minute monologues. Splitting on speaker turns gives fragments like “Yeah.” or one huge block. Windows are cut on word timestamps instead, so each has an exact start and end in the audio and keeps its speaker labels in the text.

30 · 60 · 120 s

Index three window lengths and search all of them

Long windows blur an answer into everything around it; short ones can cut an idea in half. Every recording is indexed at 30, 60 and 120 seconds, each window overlapping the next by half. Every question searches all three lengths, and the reranker decides which fits.

meaning 0.6 · keyword 0.4

Hybrid search, blended inside the database

Keyword search matches any word of the question after stemming, which catches names, numbers and jargon. Meaning search compares embeddings, which catches paraphrases. Reciprocal rank fusion blends the two rankings, 60% meaning and 40% keyword, in one SQL query per window length.

join at 5 · 15 · 30 s overlap

Join neighbouring matches into one passage

Overlapping windows mean a good stretch of audio matches several windows in a row. Within each length, matches that overlap by at least 5, 15 or 30 seconds join into one passage, capped at 90, 180 or 300 seconds. The passage text is rebuilt from the stored words, so nothing repeats.

Gemini 3.8 Flash, 0–100

Rerank passages from every length together

Scores from different lengths are not comparable, so a reranker reads the question with every candidate passage and scores how well each answers it. The active reranker is Gemini 3.8 Flash, scoring all candidates in one call. Two local rerankers are built into the same slot: GTE-ModernColBERT-v1 and Qwen3-Reranker-4B.

20 s overlap · top 5

Return each moment once

After reranking, a passage that overlaps a higher-ranked passage from the same recording by 20 seconds or more is dropped. The answer is the top five distinct moments, each with its recording, time range, speakers and text.

Database

Two tables and six indexes in one Postgres database

Everything lives in Postgres 18 with the pgvector extension: the words, the windows, the keyword index and the vector index. The service creates the extension, both tables and every index on startup if they are missing.

How a search uses them

Each search runs one SQL query per window length. Inside it, the keyword part uses the GIN index and the meaning part uses the HNSW index, each keeping its top 20 windows of that length. Reciprocal rank fusion blends the two lists, and the winners are joined back to their windows and recordings through the primary keys.

Filtered vector search

Each meaning search is limited to one window length, and a plain HNSW scan can run out of nearest neighbours before it finds 20 of that length. Every connection turns on pgvector's iterative index scan in strict order, so the scan keeps going until it has enough matches of that length, still in exact distance order.

Evaluation

How recall@k is measured

A hand-labelled set of questions, each paired with the exact stretch of audio that answers it. The eval script sends every question to the running search service and checks the time ranges it gets back against the labels.

  1. Label the answers

    37 questions written against the 36 recordings. Each answer is a time span: recording, start second and end second. 17 questions have one answer span; 20 have two or three, because the topic comes up in more than one recording.

  2. Search

    Each question goes to the running service exactly as a user would send it, asking for the top 10 passages. All four values of k are scored from that one list.

  3. Count hits

    A passage finds an answer span when it comes from the same recording and covers at least half of the span's duration.

  4. Score

    recall@k for one question is the share of its answer spans found in the top k passages. The reported number is the average over all questions.

Why the eval compares time ranges, not chunk IDs

The same moment can come back as a 30-second window or a three-minute joined passage, so chunk IDs are not a stable answer key. Comparing time ranges scores every window length the same way. Requiring half of the answer span means a passage must contain most of the answer, and the 300-second cap on joined passages limits how much a long passage can cover by luck.

Limits and next steps

What comes next

Limits of this build

  • Search speed. With the language-model reranker, a search takes 10.2 seconds on average. The local ColBERT reranker in the same slot scores in about a second on a GPU.
  • Free-tier limits. Transcription, embeddings and reranking all use the Gemini free tier, which rate-limits long recordings and bursts of searches.
  • What recall does not measure. A three-minute passage that contains a 20-second answer still counts as a hit, so timestamp precision needs its own metric.
  • A small question set. 37 questions labelled by one person is enough to catch regressions, not to compare close settings with confidence.

At larger scale

What a large, continuously growing audio library would need. None of it is built yet.

A complete ingestion pipeline

Today, transcription and indexing start when someone calls the service directly. At scale, recordings and transcripts live in object storage (S3), and Kafka events drive the work.

  1. Each upload publishes a “new audio” event.
  2. Transcription workers transcribe the audio, store the transcript in S3 and publish a “transcript ready” event.
  3. Indexing workers cut the windows, create the embeddings and write them to the search store.

This setup:

  • keeps slow, expensive work away from search traffic.
  • lets each stage scale by adding workers.
  • absorbs bursts of uploads.
  • turns rate limits and failures into retries.
  • makes it easy to re-index the whole library, for example with a new embedding model, from stored transcripts without transcribing anything again.

A dedicated search engine

Postgres handles both kinds of search well at moderate scale. For a very large library, a purpose-built search engine such as OpenSearch becomes the better fit. It is designed for exactly this workload and adds features that matter for spoken audio:

  • Dropping filler words such as “um” and “uh” while indexing, so they do not clutter matches.
  • Fuzzy search, which tolerates transcription mistakes such as a misheard or misspelled name.
  • Synonyms and phrase matching, so “GPU” can match “graphics card” and exact quotes can be found.
  • BM25 ranking by default, which gives rare, distinctive words more weight than Postgres's built-in ranking does.
  • Vector search and hybrid ranking built in, so keyword and meaning search still live in one system.
  • Horizontal scaling, by spreading the index across many machines and adding copies to handle search traffic.

Models

  • The local reranker model moved out of the web service onto its own GPU-backed service.
  • A local embedding model, removing per-request cost and rate limits, or an enterprise paid service.
  • Search filters by recording, speaker or date, using details already stored with each window.

Alternative ideas not explored (time constraints)

These alternative retrieval ideas were out of scope for this version. Each one would slot into the existing pipeline without changing the rest.

Metadata search

A language model reads every window at indexing time and tags it from a predefined set of metadata, such as the topics discussed, the people, companies and products mentioned, or whether the passage asks or answers a question. At search time, the same model tags the question with the same set.

Matching tags is a simple lookup against a standard database index, with no similarity scoring. That makes it fast and deterministic, and it would become a third search strategy alongside keyword and meaning search. Its matches would join the other candidates, and the reranker would combine them all.

Metadata search is precise on structured facts such as who, which company or which product, however the question is worded. It is also cheap at search time, because the expensive tagging happens once, when a recording is indexed.

Query expansion

A small, fast language model rewrites the question before meaning search. It adds likely phrasings, synonyms and related terms, or drafts a short example answer.

Spoken conversation is loose and informal, while typed questions are compact. Expanding the question brings it closer to how people actually talk about a topic, so meaning search finds more of the right passages. Because the model is small, it adds little delay.

Stronger reranking

The reranker slot can hold more capable models:

  • Language-model reranking. A general language model reads the question and each candidate passage and judges how well the passage answers it. It handles nuance and conversational context well, but costs more and is slower, so it suits a final shortlist. now in place: Gemini 3.8 Flash
  • Newer purpose-built models, such as Jev, recently released by TypeSafe AI. It scores every candidate passage in a single fast call and returns a relevance probability for each. Because the scores are probabilities, weak passages can be dropped outright instead of always returning a fixed number of results.
